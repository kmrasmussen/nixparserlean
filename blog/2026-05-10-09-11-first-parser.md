# First parser slice

The first useful shape of this project is deliberately small: model just enough
Nix syntax in Lean to make real parser work possible, then let the compiler keep
that model honest.

The initial AST has expressions for integers, strings, booleans, `null`,
identifiers, lists, attribute sets, recursive attribute sets, and `let ... in`.
Bindings are either assignments to attribute paths or plain `inherit` groups.
That is not the whole Nix language, but it is already enough structure to start
asking better questions:

- Which constructs should be represented as syntax only?
- Which invariants belong in the parser?
- Which invariants should be proved later over a smaller core language?

The parser is handwritten for now. That keeps the mechanics visible and gives us
a place to discover the right Lean-side model before introducing a parser
combinator layer or a more faithful grammar. It currently parses examples like:

```nix
{
  answer = 42;
  values = [ true null "nix" ];
}
```

and:

```nix
let
  x = 1;
in
  [ x "ok" false ]
```

The project is also a Nix flake now. At this stage the flake is intentionally
boring: it gives the repository a development shell with Lean and Git, and it
pins `nixpkgs` so future experiments can be reproduced.

Next I want to make the parser more Nix-like in two directions: comments and
operators. Comments will improve the everyday feel immediately. Operators will
force a real precedence table, which is probably the first point where the Lean
model needs to become more precise.
